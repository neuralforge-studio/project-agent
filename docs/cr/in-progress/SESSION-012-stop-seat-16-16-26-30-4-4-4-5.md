### 원인(측정으로 나눔)
- `stop`은 provider를 5번 관찰했습니다(`request_stop` 1번, 종료 대기 loop 4번). 관찰마다 `claude mcp serve`를 새로 띄우고 닫았습니다.
- 실제 claude(2.1.x)로 한 번의 관찰 비용을 쟀습니다(host load 46). 서버 시동 1.8~2.7초, ListAgents 0.10~0.25초, close 1.6초(`wait(1)` 1초와 terminate 0.6초). 합계 약 4~4.5초이고 `stop`은 이것을 4~5번 치릅니다. 사용자 환경의 15~53초와 같은 크기입니다.
- `claude mcp serve`는 stdin을 닫아도 끝나지 않습니다(10초 뒤에도 살아 있었고 SIGTERM 0.6초 만에 끝남). 그래서 `MCPClient.close`의 1초 대기는 항상 terminate를 늦출 뿐이었습니다.
- 한 서버를 계속 써도 ListAgents는 그 시점의 세션을 돌려줍니다. 서버를 띄운 채 tmux에서 `claude`를 시작하자 20초 뒤 목록에 나타났고, 종료하자 0.2초 뒤 사라졌습니다.
- seat·project 수에 비례하는 우리 코드의 몫(16×16 대 4×4 cProfile, 같은 `stop` 1회): tmux 호출은 24 → 22로 비례하지 않습니다(git 3). `parse_peers`가 행 × 줄로 O(N²)였고(0.47초), `load_registry`의 `_overlap`이 project 쌍마다 `.parents`를 새로 만들었습니다(0.23초). 함수 호출은 43만 → 148만이었고 대부분 `parse_peers`였습니다.
- 4×4와 16×16의 초 단위 차이는 거의 provider(가짜 claude의 ListAgents가 peer 수에 비례, 1.7초 → 6.9초)와 host load(측정 중 46~233)입니다. 이 몫은 우리 코드가 줄이지 못하고, 실제 claude의 ListAgents는 38 세션에서 0.1초였습니다.

### 변경

- `MCPClient.close`: 입력 종료 뒤 0.1초만 기다리고 terminate합니다(`EXIT_GRACE`). 이 대기는 `send`·`start`의 MCP 호출에도 같은 만큼 줄어듭니다.
